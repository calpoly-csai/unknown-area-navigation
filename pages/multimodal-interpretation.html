Multimodal Scene Interpretation

Task Definition

The multimodal scene interpretation subsystem addresses the question of what to do once an unknown or ambiguous object has been detected. Given a single image, the task is to produce two outputs: a natural-language scene description that summarises what is visible, and a binary traversability judgment — either safe to pass or not safe to pass — indicating whether the scene ahead is navigable.

This framing reduces a complex, open-ended perception problem to a structured two-output query that can be issued to any vision-language model (VLM) capable of processing image input. The binary judgment is parsed from the model's text response using a shared utility function, making the pipeline model-agnostic.

Performance Observations

Local VLMs were run on CPU without GPU acceleration. Under these conditions, inference times ranged from 10 to 30+ minutes per image, making real-time deployment entirely impractical in their current form. The bottleneck is the absence of hardware acceleration: these models are designed for GPU or dedicated edge hardware, and CPU-only execution multiplies inference time by an order of magnitude or more.

Cloud API models returned results in 2–5 seconds per image with no local hardware requirements. This represents a reduction of two to three orders of magnitude in latency compared to local inference on CPU, demonstrating substantially greater feasibility for near-term prototyping and deployment.

Shared Utilities and Correctness Validation

All VLM backends share a common set of helper functions defined in a single utilities module. These functions handle the parsing and formatting tasks that are identical across all model implementations:

  • parse_traversability — parses a model's text response and returns a boolean traversability judgment, normalising variations in phrasing to a consistent binary output.
  • build_output — constructs the structured output dictionary containing the scene description, traversability judgment, and model metadata.
  • get_output_path — derives the output file path for a given input image, ensuring consistent naming conventions across all model backends.
  • is_jpg — validates that a given file path refers to a JPEG image, filtering out non-image files before they are passed to a model.

Each of these four functions was validated using property-based testing with the Hypothesis library. A minimum of 5 correctness properties were defined per function, and each property was tested against at least 100 randomly generated examples. This approach provides stronger correctness guarantees than example-based unit tests alone, as it exercises the full input space rather than a fixed set of hand-picked cases.

Comparative Experiment Results

A comparative experiment was conducted to evaluate Gemini 2.0 Flash Lite and GPT-4o-mini on a shared 9-image test set (test1–test10, excluding test4). Both models received the same prompt and were timed using wall-clock time per API call.

On traversability accuracy, OpenAI's GPT-4o-mini achieved 88.9% (8/9) correct judgments, compared to 77.8% (7/9) for Gemini 2.0 Flash Lite. On latency, the models were closely matched: Gemini returned a mean response time of 1.944 s per image, while OpenAI returned a mean of 1.894 s per image.

Full speed and accuracy tables, along with a per-image error analysis, are available on the Experiments page.

Limitations

  • No ground-truth labels. The traversability judgments used as ground truth in the comparative experiment were assigned manually, without a formal labelling protocol or inter-annotator agreement measure.
  • CPU-only inference for local models. All local VLMs were run on CPU rather than their intended GPU or edge hardware targets. The resulting inference times are not representative of the models' performance under intended deployment conditions.
  • Single static frames with no temporal context. Each query consists of a single image. The models have no access to prior frames, motion history, or any temporal signal that might improve traversability judgment in dynamic scenes.
  • Non-representative two-image test set. The initial evaluation used only two images. The expanded comparative experiment used nine images, but this remains a small and potentially non-representative sample of real-world traversability scenarios.
