AprilTag-Based Navigation

Task Definition

Given a live camera feed, the navigation subsystem must detect an AprilTag in the current frame, estimate its 3D pose using cv2.solvePnP, and issue one of five movement states based on the tag's position relative to the camera:

  • Move Left — the tag is displaced to the left beyond the lateral threshold
  • Move Right — the tag is displaced to the right beyond the lateral threshold
  • Move Forward — the tag is aligned and beyond the stopping distance
  • Stop — the tag is within the stopping distance
  • No Tag Detected — no AprilTag is visible in the current frame

The "No Tag Detected" state is emitted whenever the detector finds no marker in the frame, allowing the system to signal loss of the navigation target explicitly rather than silently holding the last known command.

Camera Calibration

Accurate pose estimation requires knowledge of the camera's intrinsic parameters. A dedicated calibration script was developed to compute these before running the main detection loop.

Checkerboard Target

The calibration target is a checkerboard pattern with an 8×6 inner-corner grid and a 20 mm square size. Multiple images of the board at varying angles and distances were collected to ensure robust parameter estimation.

Corner Detection

For each calibration image, the frame was converted to grayscale and cv2.findChessboardCorners was used to locate the inner corners of the pattern. Corner positions were then refined to sub-pixel accuracy using cv2.cornerSubPix with a termination criterion of 30 iterations or ε = 0.001.

Intrinsic Parameter Estimation

Once corner correspondences were collected across all calibration images, cv2.calibrateCamera was called with the object-point / image-point pairs to recover the camera matrix K and distortion coefficients. The resulting parameters were saved to camera_params.npz for use in the detection script.

Coordinate Convention

The translation vector returned by pose estimation is expressed in the camera coordinate frame using the following convention:

  • X (right) — lateral offset; negative values indicate the tag is to the left, positive values to the right
  • Y (down) — vertical offset relative to the camera optical centre
  • Z (into the scene) — depth along the optical axis; represents the distance from the camera to the tag

Movement Control Logic

Directional commands are derived from the tag's translation vector using fixed thresholds. The lateral offset is checked before depth, so the agent corrects its heading before advancing toward the target.

Condition Evaluated In Order Command
pose_t[0] < −0.075 m 1st Move Left
pose_t[0] > +0.075 m 2nd Move Right
pose_t[2] ≤ 0.1 m 3rd Stop
Otherwise 4th Move Forward
No tag detected — No Tag Detected

Conditions are evaluated in the order listed. Lateral misalignment is checked before depth, ensuring the agent corrects its heading before advancing. The lateral dead-band of ±7.5 cm defines the alignment zone within which depth takes precedence.

Limitations

  • Single-tag assumption. The system assumes at most one AprilTag is present per scene. Multi-tag disambiguation logic was not implemented.
  • Discrete threshold-based commands. Movement commands are binary and threshold-based. No continuous control signal or PID controller was implemented, so the agent cannot smoothly interpolate between states.
  • No temporal smoothing. The system operates on individual frames with no filtering across time. Rapid tag movement or momentary detection failures can cause flickering command output.
  • No integration with other subsystems. The navigation subsystem operates independently. No integration with the unknown object detection or multimodal interpretation subsystems was implemented in this phase.
